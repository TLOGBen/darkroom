# P1　取回上一份時，蓋掉了 AI 代理剛存的新編輯

你在 App 按「取回上一份」的同時，AI 代理剛好幫這張照片存了一份新的編輯；取回照樣寫進去，把那份新編輯蓋掉，而它在哪裡都沒有備份。

- **不成立的規則**：R1　取回上一份編輯時，絕不蓋掉一份不同的編輯。
- **傷害**：AI 代理（或另一個分頁）剛做好的修圖不見了，也取不回來。
- **發現類型**：bug
- **圖**：diagrams.html 的最後一張

## 劇本

1. 這張照片有一份編輯 A。— `darkroom_app/services/photo_library.py:351`
2. 你在 App 清除編輯：A 被留成「上一份」，照片變成沒有編輯。— `photo_library.py:358`、`adapters/persist/edit_store.py:99`、`:101-103`、`:105`
3. 你在 App 按「取回上一份」：程式讀到「目前沒有編輯」。— `photo_library.py:366`
4. 程式讀到「上一份是 A」。— `photo_library.py:367`
5. 就在這時候，AI 代理透過 MCP 幫這張照片存了一份新的編輯 B。— `photo_library.py:351`（MCP 是另一個行程：`adapters/mcp_server/__init__.py:1`）
6. 取回繼續：它比對的是第 3 步讀到的「沒有編輯」，所以不擋，直接把 A 寫進去，B 被蓋掉。— `photo_library.py:373-376`

## 每一步都走得到嗎

1. 是，`set_edit` 寫入編輯檔。
2. 是，`clear_edit` 先留上一份再刪檔。
3. 是，`restore_edit` 先讀目前編輯。
4. 是，接著讀上一份。
5. 是：HTTP 請求跑在 worker thread（`adapters/http/server.py:130`），MCP 是另一個行程，兩者寫同一個資料夾；編輯檔的寫入沒有任何鎖（`edit_store.py:91-94` 只做整檔原子替換，`locks.held` 沒有被呼叫）。
6. 是，比對用的是第 3 步的舊快照，寫入前沒有重讀。

## 給讀者的探針

- hunt：`photo_library.py:376` 寫入之前，`:366` 讀到的目前編輯還是不是檔案裡的內容？
- prove-it 強制順序：在 `restore_edit` 執行到 `:373` 之前暫停它，期間從 MCP 呼叫 `darkroom_edit_set`（或 CLI `edit set`）存一份不同的編輯，再讓取回繼續；之後讀編輯檔，應該要是剛存的那份，實際會是上一份。
