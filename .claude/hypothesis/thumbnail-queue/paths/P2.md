# P2　直接要一張縮圖時，背景剛好把它做完，結果又被做一次

你點開一張還沒有縮圖的照片（或縮圖格要顯示它），程式先查「有沒有縮圖」：還沒有。就在它準備排進佇列的一瞬間，背景工作剛好把這張做完、離開「處理中」；於是你的請求排了一個新工作，同一張又被做一次。

- **破壞的規則**：R2　一張照片的縮圖做好之後，只有照片本身更新過，才會重新縮一次。
- **傷害**：多讀一次原圖、多算一次指紋，這次請求多等一件工作的時間；不會壞掉任何資料。
- **發現類型**：bug（浪費）
- **圖**：diagrams.html 的圖 3

## 劇本

（模型 3 張照片、2 個工作執行緒，`model/R2.cfg` 的 18 步反例）

1. 你打開縮圖格，列出資料夾：3 張都還沒有縮圖，依序排進背景佇列。— `photo_library.py:516-530`
2. 你直接要第 3 張的縮圖：程式查索引，還沒有。— `photo_library.py:543-548`
3. 背景的兩個工作執行緒把第 1、2、3 張依序拿去做；第 3 張做完、記進索引、離開「處理中」。— `photo_library.py:189-198`、`_generate :493`、`:203-206`
4. 你的請求這時才排進佇列：第 3 張已經不在「處理中」，於是建立一個新的（最優先）工作。— `photo_library.py:550` → `:143`、`:151-157`
5. 工作執行緒拿走這個新工作：第 3 張被做了第二次，照片沒有改過。— `photo_library.py:189-198`

## 每一步都走得到嗎

1. 是，同 P1 第 1 步。
2. 是：`thumbnail` 先 `lookup`＋`read`（`:543-548`），兩者都不握佇列的鎖。
3. 是：背景工作照佇列順序取（`:186-189`），不等直接請求。
4. 是：`submit` 只看 `inflight`（`:143`）；`:548` 查完到 `:550` 排入之間沒有鎖，工作做完並 `pop`（`:204`）可以落在中間。
5. 是：優先 0 的工作永遠不會被當成過期（`:190`）。

## 給讀者的探針

- hunt：`photo_library.py:550` 排入時，`:543` 查到「沒有縮圖」之後，同一張的背景工作有沒有做完並離開 `inflight`？
- prove-it 強制順序：讓 `thumbnail` 在 `:548` 之後、`:550` 之前停住，等背景把這張做完再放行；之後數這張被做了幾次，應該是 1，實際是 2。
